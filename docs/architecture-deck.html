    Tieout

    Independently-verifiable reconciliation for onchain institutional positions.
    Tie the chain out to your books — and let your examiner reproduce it, trusting no one.

    The problem

    Dana is personally accountable for positions she cannot independently verify.

    • Dana — RIA Head of Operations & Compliance. Not crypto-hostile; liability-aware.
    • Moving client assets = custody under the Investment Advisers Act custody rule.
    • Custody triggers an annual, no-notice independent verification — Form ADV-E.
    • For traditional assets a custodian's statement suffices. For onchain assets, neither Dana nor her CPA can independently verify the positions tie out.
    The gap

    Incumbents — Fireblocks/TRES, Cryptio, Bitwave — reconcile as the trusted intermediary: "trust our API, the books are right."

    Quietly re-introducing the exact trust assumption Ethereum was built to remove — reconciling from inside the trust boundary.

    If the reconciliation is wrong, it is Dana's name on the ADV-E.

    NFR-0 — the single non-negotiable

    Every decision descends from one requirement.

    NFR-0
    tieout verify re-derives the reconciliation from public chain data and reproduces the same hash on two independent machines.

    Downstream of it

    Every invariant below (AD-1…AD-17) exists to protect NFR-0. Nothing is decorative.

    A second implementation is invited

    The auditor may run an independent verifier — so the byte-level contract must be pinned, not left to implementer taste.

    Ambiguity = defect

    A rule two compliant builds could read two ways is a bug. Determinism is binary: ✅ / ❌.

    Paradigm — functional core / imperative shell

    The core is pure. The shell holds every effect.

    Ports-and-adapters at the seam. Dependency direction is one-way: shell → core only; the core imports nothing from the shell.

    The four load-bearing decisions — resolved

    Where the design could have forked, it doesn't.

    AD-6Canonical rate = event-derived

    The authoritative rate curve is a step function from Lido TokenRebased fields. The archive read is a cross-check, asserted exactly equal at rebase blocks — so the verifier never needs an archive node.

    AD-7/8Boundary = manifest + strong verify

    The sole core input is the canonical manifest + ledger. verify re-derives the manifest from public data — never trusts a shipped one.

    AD-11/12Serialization = JCS + keccak256

    Canonical JSON (RFC 8785, JCS) with string bigints, then keccak256. One named canonicalizer; the on-disk report.json is byte-identical to the hashed bytes.

    AD-14Attestation = stored registry

    A single bytes32 anchored in AttestationRegistry on Base mainnet — first-write-wins, tamper-evident, timestamped.

    The byte-level contract — why the hash reproduces

    Two compliant builds must produce the identical bytes.

    • Integers → decimal strings matching ^-?[0-9]+$, from BigInt.toString(10) only. Never a JSON number.
    • Hex (addresses, tx/block hashes, topics) → lowercase, 0x-prefixed, fixed-width. EIP-55 checksum is display-only.
    • JCS bytes → sorted keys, UTF-8, NFC, no BOM, no trailing newline (single-line).
    • Math → multiply-before-divide with exactly one floor division; non-negative bigints. No float ever touches the canonical path.
    • Window → both endpoints pinned as (blockNumber, blockHash); closed range [start, end]; latest never read.
    • Hash → Ethereum keccak256 (Keccak padding), not NIST SHA3-256.

    Every array declares a total order. JCS sorts object keys but not arrays — so events order by (blockNumber, txIndex, logIndex), which is also the dedup key (AD-4), and report lots order by acquisition (AD-13).

    Attestation — what the chain does & doesn't prove

    Tamper-evidence + a commitment timestamp. Nothing more.

    contracts/AttestationRegistry

    attest(bytes32 reportHash)
    first-write-wins · reverts on duplicate
    stores { uint64 blockNumber, uint64 timestamp }
    emits Attested(reportHash, submitter, timestamp)

    One anchored value: reportHash. Tested on Anvil → dry-run on Base Sepolia → single canonical anchor on Base mainnet.

    It proves

    • reportHash existed / was committed at or after a block.
    • The record is tamper-evident thereafter.

    It does NOT prove

    • NOTcorrectness — that comes solely from verify re-derivation.
    • NOTidentity — submitter is a recorded fact, not a signature over the report.
    What it deliberately does NOT claim

    The honesty guardrail matters as much as the claim.

    AD-16Derivation, not the books

    A reproduced hash attests the onchain-derived position and the commitment to it — never the honesty or completeness of the private books. A green verify means "derivation reproduced," not "the books are right." Report text, UI, and verify output must say so.

    AD-17Narration from real facts only

    The explain-itself narration is generated solely from recon's real diff — event id, block, delta, cause — via deterministic templating. No hand-authored numbers or causes on the canonical path. Purely presentational, UI-only text is marked non-canonical and excluded from the hash.

    The unfair advantage isn't a technical moat — it's Series-65 fluency landing the guardrails exactly where most engineers get them subtly, dangerously wrong.
