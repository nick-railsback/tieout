# Ponder — sync engine internals (backfill, reorgs, checkpoints, RPC)

How Ponder actually fetches, caches, and orders onchain data. This is the contributor/debugging view of the `sync-historical`, `sync-realtime`, `sync-store`, `rpc`, and `runtime` subsystems. ## Checkpoints (the ordering primitive)

The linchpin of the whole engine is the **checkpoint**: a fixed-width, zero-padded string encoding `blockTimestamp · chainId · blockNumber · transactionIndex · eventType · eventIndex` ([utils/checkpoint.ts#L35-L40](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/utils/checkpoint.ts#L35-L40)). Because every component is fixed-width and padded, plain lexicographic string comparison equals chronological order — which is what lets Ponder merge events from many chains into one deterministic omnichain stream. `encodeCheckpoint`/`decodeCheckpoint`/`blockToCheckpoint` live at [utils/checkpoint.ts#L44-L75](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/utils/checkpoint.ts#L44-L75), with a `MAX_CHECKPOINT` sentinel standing in for "end of time" during finality math.

## Historical sync (backfill)

Backfill's hardest problem is `eth_getLogs` range sizing, since every provider caps it differently. Ponder starts with a 500-block estimate and adapts: on an error it parses the provider's suggested range via `getLogsRetryHelper()`, and when no hint is available it grows the window ~5% at a time — `chain.ethGetLogsBlockRange` forces a fixed size ([sync-historical/index.ts#L136-L275](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-historical/index.ts#L136-L275)). Multiple addresses are batched in groups and fragile topic filters have their trailing nulls trimmed before the call.

Factory child-address discovery scans the factory's creation event, extracts each child address from the log, and records the block where it first appeared so later runs reuse the set ([sync-historical/index.ts#L361-L431](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-historical/index.ts#L361-L431)). Per-block fetching is bounded by an in-memory budget, `MAX_BLOCKS_IN_MEM = max(finalityBlockCount * 2, 100)`, so a fast backfill can't exhaust memory ([sync-historical/index.ts#L1030-L1051](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-historical/index.ts#L1030-L1051)). Receipts are fetched with `eth_getBlockReceipts` when supported, falling back to per-transaction `eth_getTransactionReceipt` ([sync-historical/index.ts#L286-L333](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-historical/index.ts#L286-L333)).

## Realtime sync & reorg handling

Realtime sync keeps a linked list of `unfinalizedBlocks` where each block links to its parent by hash, plus per-block snapshots of discovered factory children for rollback ([sync-realtime/index.ts#L109-L135](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-realtime/index.ts#L109-L135)). To avoid an `eth_getLogs` per block it checks the block's logsBloom first: `isFilterInBloom()` hashes the filter's address/topics and tests three bit positions in the 256-byte bloom, skipping the fetch when the bloom is empty or the filter can't match ([sync-realtime/bloom.ts#L40-L102](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-realtime/bloom.ts#L40-L102)). Bloom checks yield false positives but never false negatives, so correctness holds while most no-log blocks skip the call.

Reorg reconciliation pops unfinalized blocks until it finds one whose hash matches the new block's parent, rolls back the store to that ancestor, and removes the reorged blocks' discovered child addresses ([sync-realtime/index.ts#L909-L941](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-realtime/index.ts#L909-L941)). If no matching ancestor exists in the unfinalized set, the reorg is **deeper than finality and fatal** — Ponder throws "unrecoverable reorg beyond finalized block" rather than silently corrupting data ([sync-realtime/index.ts#L914-L932](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-realtime/index.ts#L914-L932)). A block finalizes once the tip advances `2 * finalityBlockCount` beyond it, at which point its state is committed and its snapshots are freed ([sync-realtime/index.ts#L1154-L1197](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-realtime/index.ts#L1154-L1197)).

## The sync store (RPC cache)

The sync store is a Postgres/PGlite cache of raw RPC data (blocks, logs, transactions, receipts, traces) that survives restarts and amortizes across runs. Completed ranges are tracked per filter fragment using Postgres `nummultirange`; `insertIntervals()` rounds interval ends up on write and down on read so that half-open range unions compose correctly ([sync-store/index.ts#L208-L279](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-store/index.ts#L208-L279)). On top of interval tracking there's a second cache layer keyed by request hash — `insertRpcRequestResults()` / `getRpcRequestResults()` memoize expensive calls (e.g. `context.client` reads) and are pruned on reorg ([sync-store/index.ts#L172-L189](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-store/index.ts#L172-L189)). Raw rows are stored under the `ponder_sync` schema keyed by `(chainId, blockNumber[, index])` ([sync-store/schema.ts#L41-L70](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-store/schema.ts#L41-L70)).

## The RPC layer

The RPC layer does adaptive, latency-aware load balancing across endpoints. Each endpoint gets a "bucket" holding its hostname, a dynamic `rpsLimit` (starting at 20), and a rolling window of latencies ([rpc/index.ts#L284-L308](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/rpc/index.ts#L284-L308)). Bucket selection is ε-greedy: ~10% of the time it explores a random available bucket, otherwise it exploits the fastest one, only switching if the alternative is meaningfully faster ([rpc/index.ts#L341-L403](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/rpc/index.ts#L341-L403)). Failures back off exponentially over up to 9 retries; a 429/timeout marks the bucket inactive and cuts its RPS limit, while sustained success slowly raises it ([rpc/index.ts#L545-L677](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/rpc/index.ts#L545-L677)). New-head discovery prefers a WebSocket subscription and falls back to polling `eth_getBlockByNumber` at `pollingInterval` when no `ws` is set or the socket fails repeatedly. The standardized request wrappers (`eth_getBlockByNumber`, `eth_getLogs`, `eth_getBlockReceipts`, …) live in [rpc/actions.ts#L28-L159](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/rpc/actions.ts#L28-L159).

## Runtime orchestration

`SyncProgress` tracks each chain's `start`/`end`/`current`/`finalized` positions and exposes `getCheckpoint()` ([runtime/index.ts#L41-L51](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/runtime/index.ts#L41-L51)). When `chain.disableCache` is true the runtime clears the interval map so every range is re-fetched even if previously synced (raw data still lands in the sync store, but no interval is ever marked complete) ([runtime/index.ts#L216-L248](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/runtime/index.ts#L216-L248)). Under `ordering: "omnichain"`, events can only be emitted up to the minimum finalized checkpoint across all chains, so a lagging chain holds back the others; `"multichain"` drops that barrier ([config/index.ts#L9-L18](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/config/index.ts#L9-L18)).

## Gotchas

- **Reorgs beyond finality are unrecoverable** and crash the process by design — size `finalityBlockCount` to the chain's economic finality, not its block time ([sync-realtime/index.ts#L914-L932](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-realtime/index.ts#L914-L932)).
- **`disableCache` is a 2–5× backfill slowdown** because intervals never complete; use it only to debug bad RPC data ([runtime/index.ts#L216-L248](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/runtime/index.ts#L216-L248)).
- **New factory children created after a completed sync** aren't discovered until the next sync run, since discovery keys off the factory event scan, not a live subscription ([sync-historical/index.ts#L361-L431](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-historical/index.ts#L361-L431)).
- **Receipt strategy is sticky**: once a chain falls back to per-tx receipts it stays there for the run ([sync-historical/index.ts#L286-L333](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/sync-historical/index.ts#L286-L333)).
