# Ponder — querying indexed data (GraphQL, SQL-over-HTTP, client, React)

Ponder exposes the indexed store four ways: an auto-generated GraphQL API, SQL-over-HTTP, the `@ponder/client` SDK, and `@ponder/react` hooks — plus custom Hono routes. Citations pin to commit `c8f6935fb65176c01b40cae9056be704c0e5318e`.

## GraphQL API

The `graphql()` Hono middleware serves the API (and GraphiQL on GET); you mount it in `src/api/index.ts` with `{ schema, db }` ([graphql/middleware.ts#L30-L97](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/graphql/middleware.ts#L30-L97)). `buildGraphQLSchema()` generates the schema from your tables, views, and relations: each table gets a singular query (lowercased name) and a plural query (name + `s`); views get only the plural form ([graphql/index.ts#L525-L597](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/graphql/index.ts#L525-L597)). Plural queries take `where`, `orderBy`, `orderDirection`, `limit`, `offset`, and cursor args `before`/`after`, returning a page with `items`, `pageInfo`, and `totalCount` ([graphql/index.ts#L554-L576](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/graphql/index.ts#L554-L576)).

The `where` input supports a rich operator set per column type — equality and `_not` universally; `_in`/`_not_in` for scalars; `_gt`/`_lt`/`_gte`/`_lte` for numerics; `_contains`/`_starts_with`/`_ends_with` (and `_nocase` variants) for strings; `_has`/`_not_has` for arrays — combinable with `AND`/`OR` ([graphql/index.ts#L1019-L1038](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/graphql/index.ts#L1019-L1038)). Queries are guarded by graphql-armor limits with Apollo-style defaults: `maxOperationTokens` 1000, `maxOperationDepth` 100, `maxOperationAliases` 30 ([graphql/middleware.ts#L32-L46](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/graphql/middleware.ts#L32-L46)).

## SQL over HTTP

The `client()` middleware exposes two GET endpoints under `/sql/*`: `/sql/db` runs a query once and caches the result, and `/sql/live` returns a Server-Sent Events stream that pushes on change ([client/index.ts#L75-L551](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/client/index.ts#L75-L551)). Live queries are invalidated via Postgres LISTEN/NOTIFY when a referenced table changes, and concurrent live connections are capped at `MAX_LIVE_QUERIES = 1000` ([client/index.ts#L36](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/client/index.ts#L36)). Every query is parsed and sandboxed: single statement only, SELECT-only allowlist, ≤5000 chars, run in a `READ ONLY` transaction with a 500 ms `statement_timeout` ([utils/sql-parse.ts#L56-L111](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/utils/sql-parse.ts#L56-L111)). This is what makes it safe to expose the SQL endpoint directly to a frontend.

## `@ponder/client`

`@ponder/client` (v0.16.6) is the typed SDK for SQL-over-HTTP. `createClient(baseUrl, { schema })` returns a client with a read-only Drizzle `db` (no insert/update/delete/transaction), a `live(queryFn, onData, onError?)` method backed by EventSource, and `getStatus()` ([packages/client/src/index.ts#L120-L276](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/client/src/index.ts#L120-L276)). The `Client<schema>` type pins those members ([packages/client/src/index.ts#L47-L80](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/client/src/index.ts#L47-L80)), and the package re-exports the Drizzle query helpers (`eq`, `gt`, `and`, `or`, `desc`, `sum`, `count`, …) so you build queries with full type-safety and no codegen ([packages/client/src/index.ts#L278-L313](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/client/src/index.ts#L278-L313)).

## `@ponder/react`

`@ponder/react` (v0.16.6) wraps the client for React on top of `@tanstack/react-query`. It exports `PonderProvider` (takes a `client`) and the hooks `usePonderQuery`, `usePonderStatus`, `usePonderClient`, and `usePonderQueryOptions` ([packages/react/src/index.ts#L1-L17](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/react/src/index.ts#L1-L17)). `usePonderQuery({ queryFn, live?, ...options })` runs a Drizzle query and, with `live` defaulting to true, subscribes via `client.live()` and sets `staleTime` to Infinity so react-query treats the SSE push as the source of truth ([packages/react/src/hook.ts#L18-L63](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/react/src/hook.ts#L18-L63)). `usePonderStatus` is a convenience hook over `_ponder_checkpoint` for per-chain progress ([packages/react/src/hook.ts#L83-L121](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/react/src/hook.ts#L83-L121)).

## Custom API routes

Beyond the built-in middleware you can export a Hono app from `src/api/index.ts`; the server mounts it at the root ([server/index.ts#L125](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/server/index.ts#L125)). Inside those routes you get a read-only Drizzle `db` and per-chain viem `publicClients` from the `ponder:api` virtual module, and the full Drizzle builder with no SQL sandbox restrictions — the right place for joins, aggregates, or logic that mixes indexed data with live RPC reads. The same server also serves `GET /metrics`, `/health`, `/ready`, and `/status`, and enables permissive CORS by default ([server/index.ts#L74-L126](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/server/index.ts#L74-L126)).

## Choosing a mode & gotchas

GraphQL is best for exploratory/mobile clients; SQL-over-HTTP with `@ponder/client`/`@ponder/react` is the recommended path for production frontends (full type-safety, live updates, no codegen); custom API routes are for anything needing server-side logic or RPC access ([docs/pages/docs/query/api-endpoints.mdx#L52-L105](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/docs/pages/docs/query/api-endpoints.mdx#L52-L105)). Two practical gotchas: `onchainTable`s support both offset and cursor pagination but `onchainView`s support offset only ([graphql/index.ts#L578-L597](https://github.com/ponder-sh/ponder/blob/c8f6935fb65176c01b40cae9056be704c0e5318e/packages/core/src/graphql/index.ts#L578-L597)); and `totalCount` can be slow on large result sets, so fetch it on the first page only and paginate with cursors thereafter.
